MyBookstore - Rapport final detaille (GLID-2 2025/2026)

0) Objectif et perimetre

Objectif: realiser une application web MyBookstore avec front-office + back-office.

Acteurs: Visiteur, Abonne, Agent, Administrateur.

Le projet respecte les roles, les menus, et le parcours de commande.

Ce rapport est prepare pour une soutenance technique: il explique le pourquoi des choix et le fonctionnement interne.

0.1) Architecture generale

Architecture MVC de Symfony:

  • Controleurs: gerent les routes et l orchestration (ex: CartController, DashboardController).
  • Entites/Repository: modele de donnees + requetes (ex: Livre, LivreRepository).
  • Templates Twig: vues front et back-office.
  • Services: logique metier reutilisable (ex: CartService).

1) Prerequis techniques

  • PHP 8.2+
  • Composer
  • Symfony CLI (optionnel)
  • XAMPP (MariaDB 10.4.x)

Serveur MySQL/MariaDB actif sur 127.0.0.1:3306.

2) Initialisation du projet

Creation du projet Symfony webapp.

symfony new MyBookstore --webapp

Configuration DB dans .env.local:

DATABASE_URL="mysql://root:@127.0.0.1:3306/mybookstore?serverVersion=10.4.32-MariaDB&charset=utf8mb4"

Creation de la base:

php bin/console doctrine:database:create

3) Conception du modele de donnees

Entites crees (conformes a l enonce):

  • User (email, roles, password, prenom, nom, telephone, adresse, isVerified)
  • Auteur (nom, prenom, bio)
  • Editeur (nom, adresse, telephone, email)
  • Categorie (nom, description)
  • Livre (titre, isbn, description, prix, stock, image, datePublication, auteur, editeur, categorie)
  • Commande (createdAt, statut, total, user)
  • LigneCommande (quantite, prixUnitaire, livre, commande)

Relations principales:

  • Livre -> Auteur / Editeur / Categorie (ManyToOne)
  • Commande -> User (ManyToOne)
  • Commande -> LigneCommande (OneToMany, cascade persist)
  • LigneCommande -> Livre (ManyToOne)

Explication: ce modele permet de separer les entites de reference (Auteur, Editeur, Categorie) du catalogue (Livre) et des transactions (Commande, LigneCommande). Chaque commande est reliee a un utilisateur et contient ses lignes de commande.

Pourquoi LigneCommande? Permet de garder l historique des prix et quantites par commande, meme si le prix du livre change plus tard.

Generation des migrations et schema DB:

php bin/console make:migration php bin/console doctrine:migrations:migrate

4) Securite et roles

Roles imposes:

  • ROLE_ABONNE
  • ROLE_AGENT
  • ROLE_ADMIN

Hierarchie: ADMIN > AGENT > ABONNE.

Acces dashboard uniquement ROLE_AGENT/ROLE_ADMIN.

Acces gestion utilisateurs uniquement ROLE_ADMIN.

Acces commandes: ROLE_AGENT peut consulter, ROLE_ADMIN peut modifier.

Explication: la hierarchie garantit que ADMIN herite des droits AGENT et ABONNE. L AGENT peut gerer les donnees vitrine et consulter les commandes, tandis que l ADMIN peut les modifier.

ROLE_AGENT est l equivalent de ROLE_USER, mais ici le role USER par defaut a ete evite pour respecter l enonce.

5) Authentification (login / register)

Generation de l authentification:

php bin/console make:security:form-login php bin/console make:registration-form

Inscription enrichie avec prenom, nom, telephone, adresse.

Role par defaut: ROLE_ABONNE.

Explication: l authentification gere la connexion et l inscription. Un visiteur peut creer un compte, puis devient automatiquement Abonne.

Le mot de passe est stocke hash et jamais en clair.

7) Back-Office (Dashboard)

Menu conforme a l enonce:

  • Auteurs
  • Editeurs
  • Categories
  • Livres
  • Commandes
  • Utilisateurs (admin seulement)

CRUD generes avec Symfony Maker:

php bin/console make:crud Auteur php bin/console make:crud Editeur php bin/console make:crud Categorie php bin/console make:crud Livre php bin/console make:crud Commande php bin/console make:crud User

Restrictions:

  • ROLE_AGENT: acces dashboard
  • ROLE_ADMIN: gestion utilisateurs + roles + reset mot de passe

Explication: le dashboard centralise la gestion des donnees vitrines. L admin dispose en plus de la gestion des comptes.

Les routes du back-office sont sous /dashboard pour isoler l administration.

Une interface admin supplementaire est realisee avec EasyAdminBundle, accessible via /admin (ROLE_ADMIN).

8) Couverture des livres (upload)

Chaque livre a une image de couverture. Upload gere dans le back-office.

Dossier de stockage:

public/uploads/covers

Affichage de la couverture dans les listes et details.

Explication: au moment de creer ou modifier un livre, l image est chargee et stockee dans le dossier public. L URL est ensuite affichee en front et back-office.

Dans une evolution, on pourrait gerer la suppression des anciens fichiers lors d un remplacement.

9) Front-Office (site vitrine)

Pages publiques:

  • Accueil: categories, editeurs, derniers livres
  • Catalogue livres
  • Detail livre (description complete)

Recherche multi-criteres:

  • Titre
  • Auteur
  • Editeur
  • Categorie

Routes utiles:

  • /
  • /livres
  • /livres/{id}

Un bouton "Voir details" est ajoute dans le catalogue pour consulter la description complete du livre.

Explication: la vitrine expose les categories, editeurs et livres, et permet a un visiteur de decouvrir le catalogue.

La recherche est realisee par une requete dynamique dans LivreRepository (filtrage multi-criteres).

10) Panier et validation de commande

Le panier est stocke en session.

Le client ajoute un livre, puis valide pour creer une commande.

Routes:

  • /panier
  • /panier/ajouter/{id}
  • /panier/supprimer/{id}
  • /panier/valider

Le back-office permet de suivre les commandes.

Explication: le panier est un stockage temporaire. La commande n est creee qu apres validation, conformement a l enonce.

La creation de commande se fait en une seule transaction: Commande + LigneCommande.

Validation du stock: si le stock est insuffisant, la commande est refusee. Apres validation, le stock est decremente.

11) Profil abonne

Chaque abonne peut modifier:

  • Email
  • Adresse
  • Telephone
  • Mot de passe

Route: /profile

Explication: cette page permet a l abonne de mettre a jour ses informations personnelles et son mot de passe.

Le changement de mot de passe exige le mot de passe actuel (UserPassword constraint).

11.1) Historique des commandes (abonne)

Chaque abonne peut consulter ses commandes dans une page dediee.

Route: /mes-commandes

Explication: cette page affiche l historique (date, statut, total) et permet de verifier les achats precedents.

L agent herite ROLE_ABONNE, donc il accede aussi a la vitrine et a l historique des commandes.

12) Redirection apres login

Admin redirige vers / (vitrine) pour travailler sur le front + acces EasyAdmin via menu.

Agent redirige vers /dashboard.

Abonne redirige vers / (front-office).

Explication: l admin gere les donnees via EasyAdmin, tandis que l agent utilise le dashboard classique.

Implementation via un LoginSuccessHandler personnalise + regle access_control sur /dashboard.

13) Guide d execution pas a pas

  1. Demarrer XAMPP et activer MySQL.
  2. Lancer le serveur Symfony:
php -S 127.0.0.1:8000 -t public

Acces front-office: http://127.0.0.1:8000/

Acces dashboard (admin): http://127.0.0.1:8000/dashboard

Explication: utilisez un compte admin pour gerer les donnees (auteurs, editeurs, categories, livres, commandes, utilisateurs).

16) Questions techniques possibles (soutenance)

Q: Pourquoi utiliser une table LigneCommande?

R: Pour conserver l historique de chaque livre commande (prix, quantite) et permettre plusieurs livres par commande.

Q: Comment garantir que seuls les admins gerent les utilisateurs?

R: Les routes /dashboard/utilisateurs sont protegees par l attribut IsGranted('ROLE_ADMIN').

Q: Comment eviter qu un abonne accede au dashboard?

R: Access control dans security.yaml + redirection apres login.

Q: Comment fonctionne le panier?

R: Stockage en session. A la validation, creation d une Commande et de LigneCommande, puis vidage du panier.

Q: Pourquoi les mots de passe ne sont pas affiches?

R: Pour des raisons de securite. Le hash est stocke en base et ne doit jamais etre montre.

Q: Comment est implemente l upload des images?

R: Le formulaire livre utilise un FileType non mappe, puis le fichier est deplace dans public/uploads/covers.

Q: Comment ajouter un nouveau role?

R: Ajouter le role dans la hierarchie et mettre a jour le formulaire UserType.

17.1) Description des fichiers principaux

Cette section explique les fichiers cles pour comprendre rapidement le projet.

Entites (modele de donnees)

  • src/Entity/User.php: utilisateur avec roles et informations personnelles.
  • src/Entity/Livre.php: livre avec auteur, editeur, categorie, prix, stock, image.
  • src/Entity/Auteur.php, Editeur.php, Categorie.php: tables de reference.
  • src/Entity/Commande.php et LigneCommande.php: commandes et details.

Controleurs (routes)

  • src/Controller/HomeController.php: accueil front-office.
  • src/Controller/FrontLivreController.php: catalogue et detail livre.
  • src/Controller/CartController.php: panier + validation.
  • src/Controller/ProfileController.php: profil abonne.
  • src/Controller/OrderHistoryController.php: historique commandes abonne.
  • src/Controller/DashboardController.php: accueil dashboard.
  • src/Controller/*Controller.php: CRUD back-office.

Formulaires

  • src/Form/RegistrationFormType.php: inscription.
  • src/Form/UserType.php: gestion users (admin).
  • src/Form/LivreType.php: creation/modif livre + upload.
  • src/Form/ProfileFormType.php + ChangePasswordFormType.php: profil abonne.

Services et securite

  • src/Service/CartService.php: logique panier (session).
  • src/Security/LoginSuccessHandler.php: redirection apres login.
  • config/packages/security.yaml: roles + acces.

Repositories

  • src/Repository/*Repository.php: requetes vers la base (ex: searchByCriteria dans LivreRepository).
  • Les repositories sont injectes dans les controllers pour lire les donnees.

Controllers

  • Les controllers recoivent les requetes HTTP, appellent services/repositories, puis rendent les templates.
  • Les routes sont definies via attributs #[Route] dans chaque controller.

Fichiers YAML (configuration)

  • config/packages/security.yaml: roles, firewalls, access_control.
  • config/packages/doctrine.yaml: connexion DB et mapping.
  • config/services.yaml: parametres et services (ex: covers_directory).

Templates Twig

  • templates/base.html.twig: layout global + menu.
  • templates/front/*: pages vitrine.
  • templates/dashboard/*: back-office.
  • templates/cart/index.html.twig: panier.
  • templates/profile/index.html.twig: profil.

Autres

  • migrations/*: scripts SQL Doctrine.
  • public/uploads/covers: couvertures des livres.

Dossiers techniques (vendor, var)

  • vendor/: dependances installees par Composer (Symfony, EasyAdmin, etc.). A ne pas modifier.
  • var/: cache, logs et fichiers temporaires generes par Symfony.

Structure generale du projet

  • src/: code PHP (controllers, entites, services).
  • templates/: vues Twig.
  • config/: configuration YAML.
  • public/: fichiers accessibles via le navigateur.
  • migrations/: versions de schema DB.
  • vendor/: bibliotheques tierces (Composer).
  • var/: cache et logs (runtime).

15) Commandes utilisees (liste complete + explications)

Les commandes ci-dessous sont les principales commandes Symfony utilisees pour realiser rapidement un projet complet.

Creation du projet

Creer un projet web Symfony avec les paquets courants (Twig, Doctrine, Security, etc.).

symfony new MyBookstore --webapp

Base de donnees

Creer la base de donnees configuree dans DATABASE_URL.

symfony console doctrine:database:create

Avant la commande, il faut renseigner correctement DATABASE_URL dans .env.local.

Creation d une classe entite

Generer une entite Doctrine et ses champs (ex: Livre, Auteur, User...).

symfony console make:entity

Exemples utilises:

php bin/console make:entity User php bin/console make:entity Livre

Creation d un script de migration

Detecter les changements dans les entites et generer un script SQL de migration.

symfony console make:migration

Execution des migrations

Appliquer les migrations pour creer/mettre a jour les tables en base.

symfony console doctrine:migrations:migrate

Generation du CRUD

Creer automatiquement un controleur, un formulaire et des templates CRUD.

symfony console make:crud

Exemples utilises:

php bin/console make:crud Auteur php bin/console make:crud Livre

Authentification

Generer les pages de login et l authentificateur.

php bin/console make:security:form-login

Generer le formulaire d inscription.

php bin/console make:registration-form

Creation des comptes (hash + insertion)

Hasher un mot de passe puis inserer l utilisateur en base.

php bin/console security:hash-password "khaled2003" php bin/console security:hash-password "oussama2002" php bin/console doctrine:query:sql "INSERT INTO user (...)"

Serveur local

Demarrer un serveur PHP local pour tester le projet.

php -S 127.0.0.1:8000 -t public

Autres commandes utiles

Ecraser la base de donnees (suppression forcee):

symfony console doctrine:database:drop --force

Creer une classe formulaire:

symfony console make:form

Creer un controleur:

symfony console make:controller

Creer un projet microservice:

symfony new nomProjet

Telecharger un projet DEMO:

symfony new --demo nomProjet

Verifier les prerequis systeme:

symfony check:requirement

Auditer la securite des dependances:

symfony console security:check

Conclusion

Le projet est complet et conforme au cahier des charges. Si le TD persistance impose des champs/relations particuliers, il suffit d ajuster les entites et de regenirer une migration.
